# 文档沉淀（overview + implement_log）

实现完成后手动唤起：把本次改动的「总览」写进 overview.md，把「实现步骤」写进 implement_log.md，两者落同一目录。overview 是总览，只更新涉及章节，绝不把逐步实现写进去；步骤全部进 implement_log.md。

> 「总览类文档」= overview.md 及其同目录专题子文档（如 image-bar.md / viewmodel-events.md / draft.md，即 overview「专题文档索引」链接的那些）。总览类文档只写设计/总览/接口契约，**一律不放实现步骤**。实现步骤的唯一归宿是与 overview.md 同目录的 implement_log.md——无论总览写进 overview.md 还是某专题子文档，步骤都追加到该目录 implement_log.md，不存在则新建。

## 执行流程

### 步骤 1：收集输入
- `$ARGUMENTS` 非空 → 作为「需求/bug 上下文 + 背景信息」，从中识别用户指明的参考文档路径（如 `xxx/overview.md`、`TECH_SPEC.md`）。
- `$ARGUMENTS` 为空 → 用 AskUserQuestion 让用户在 Other 中输入：上下文 + 背景信息 + 参考文档路径。
- 仅做文档沉淀，不拉 TAPD/Figma；若用户只给了单号，回头在步骤 1 的 Other 里补上下文。

### 步骤 2：确定目标文档路径（固定为 docs/，无需确认）
目标目录固定为项目根目录 `docs/`（即 `<仓库根>/docs/`）。overview.md 与 implement_log.md 都写入此目录，无需用 AskUserQuestion 确认路径。

- 若 `docs/` 目录不存在 → 先 `mkdir -p docs/` 再写入。
- 若 `docs/` 下已有 overview.md / implement_log.md → 直接在该目录下更新/追加。

### 步骤 3：读取参考与现有文档
- Read 用户指明的参考文档（既有 overview / solution / TECH_SPEC 等），理解结构与已记录内容。读取失败则跳过并说明，不猜路径、不中断。
- Read 目标目录下已有的 `overview.md`（若存在）掌握现有章节，判定哪些涉及本次改动。
- Read 目标目录下已有的 `implement_log.md`（若存在）掌握已有步骤最大编号，以便续编 `第N轮`。
- grounding（可选，best-effort）：`git status --short` / `git diff --stat` / `git log -1 --format=%h` 取改动文件清单与 commit。git 无改动（已在别处提交 / 补记旧改动）则回退到用户上下文与参考文档，不阻塞、不执行任何写操作。

### 步骤 4：更新 overview.md（总览＝整体功能实现概括，先整合后新增）
> overview 是「整体功能当下的实现概括」，不是改动流水账：每次把本次改动**折进**现有概括，而不是为每个需求/每轮改动追加一段。

- 不存在 → 按「overview 模板」新建。
- 已存在 → 按「先整合、后新增」判定，禁止重写无关章节：
  1. **先判是否已被覆盖**：逐节比对现有 overview，看本次改的能力是否已在某节描述过。
     - 已描述到（扩展/修复某个已有模块的行为）→ 原地修改该节要点，**不新增章节、不另起一段**。
     - 全新功能/特性（现有章节完全无覆盖）→ 才在「实现摘要」新增一个模块小节；需独立详述时新增专题子文档并在「专题文档索引」补链接。
  2. `涉及文件清单`：新增/修订对应文件行。
  3. `架构设计` / `需求概述`：仅当本次改动确实改变架构/范围时更新。
- **三条红线（任一出现即等于把 implement_log 写进了 overview）**：
  - 禁日期小节：不得有 `### xxx（2026-07-10）` 这类按轮次/日期追加的小节——overview 不带时间轴，每轮改动只折进现有概括。
  - 禁决策表：不得有 `## 决策记录` / `### 实现方案决策` / `| 决策项 | 结论 |` 等任何形式的决策表——方案选型与理由只进 implement_log「探索与决策」。
  - 禁步骤化：不得有「第N轮 / 输入： / 行为： / 文件变更表」等步骤或逐改动清单——步骤唯一归宿是 implement_log。
- 写完自检：确认 overview.md 及同目录专题子文档不含上述三类痕迹；改完读起来像一次性写就的总览，而非多轮拼贴。

### 步骤 5：更新 implement_log.md（步骤日志，追加，实现步骤的唯一归宿）
- 位置：与 overview.md 同目录。即使用户把总览写进了某专题子文档（如 image-bar.md），实现步骤仍追加到该子文档同目录的 implement_log.md，**不写进子文档本身**；同目录没有 implement_log.md 则新建。
- 不存在 → 按「implement_log 模板」新建文件头 + 首轮。
- 已存在 → 文末追加一段新日期小节，步骤编号续接已有最大编号。
- 每步记录「Agent 交互细节流程 + 最终改动」（见「implement_log 单轮模板」）。

### 步骤 6：补全关键词路由（按需）

关键词路由是多级的：`docs/README.md` 的「关键词路由」表只把关键词导向模块 .md
（如 topic.md）；summary 文档实际挂在更深——模块 .md 的子模块表（如 topic.md「模块」表）
与其指向的详情清单（如 topic_detail.md）的内联链接里。

判断已覆盖：沿本次关键词在 README 命中的模块 .md **逐级往下 Read**（子模块表 → 详情清单），
看本次 overview.md 是否已被链接、或同级条目已覆盖相同范围。任一级已覆盖 → 跳过，不动任何文件。

未覆盖 → 在最贴近的一级补链接（相对 `docs/` 写路径，到 `docs/` 用
`../../docs/.../overview.md`）：
- 既有模块下的新子模块/summary → 在该模块 .md 子模块表末追加一行（子模块名 / 一行职责 / overview.md 链接）
- 全新顶层主题、README 一级表无任何行命中 → README 一级表追加「关键词 → 该 overview.md」一行

### 步骤 7：收尾
逐一 Read 写过的两份文档做减法检查：去重复、压理由、不留对话痕迹。最后简述：写入了哪两个文件、overview 改了哪些章节、implement_log 追加了哪几轮、是否补了路由行。
- 目录不存在导致 Write 失败时，对 `docs/` 目录 `mkdir -p` 后重试。

## overview 模板（不存在时新建，已存在时仅更新涉及章节）

结构：

- `# overview — <主题>`
- `## 需求概述`（一段话：本次实现/改动范围）
- `## 架构设计`（数据流 / 分层 / 关键约束，按组件分小节）
- `## 实现摘要`（### 模块/组件 — 要点：职责、关键 API、行为）
- `## 涉及文件清单`（表：文件路径）
- `## 专题文档索引`（可选：同级详情文档链接）

## implement_log 模板（首次创建时文件头）

```
# implement_log — <主题>

> 实现步骤日志：每段一轮，记录 Agent 交互细节流程与最终改动。统一追加到文末，编号递增。
```

## implement_log 单轮模板（每轮复制此块，追加到文末）

骨架取自 `docs/overview.md`「实现过程与指令记录」（输入/行为）；`最终改动` 行为级粒度参考 `docs/implement_log` §7 修复策略，但不引入 §7 的现象/根因/融合规则。

```
### 第N轮：<一句话标题> [YYYY-MM-DD]
- **输入**：本次给到 agent 的指令/上下文（用户原话或要点概括；多轮讨论只取与本步直接相关者）。
- **探索与决策**：agent 探索了哪些代码/文档，遇到什么权衡，最终怎么决定（行为级，不贴代码）；关键决策点可列选项/选择/理由。
- **最终改动**：
  - `<文件路径>` — 新增/修改：<方法名 / 属性 / 类 / 枚举>，行为级要点。
  - `<文件路径>` — ...
- **验收**：编译通过 / 结果说明（如有；无则省略）。
- **commit**：`<7位 hash>`（git 取得；无则留空）。
```
